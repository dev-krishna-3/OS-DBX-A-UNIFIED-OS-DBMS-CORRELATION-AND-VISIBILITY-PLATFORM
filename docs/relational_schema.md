# OS-DBX — Relational Schema

**Project:** OS-DBX — Unified OS + DBMS Correlation and Visibility Platform  
**Database:** MySQL  
**Backend:** FastAPI  
**Frontend:** React  
**OS Platform:** Linux  
**Schema Version:** 1.0  
**Status:** Frozen Baseline

---

## 1. Purpose

The OS-DBX relational database is designed to store, organize, and connect
information generated by both the Linux Operating System layer and the DBMS
layer.

The database is divided into four major logical areas:

1. **OS / Linux Monitoring**
2. **OS Simulation**
3. **DBMS Management**
4. **Cross-Layer Correlation and Analysis**

The most important purpose of the schema is to establish a relationship
between:

```text
Linux Process
      ↓
OS Event
      ↓
DBMS Transaction
      ↓
Transaction Operation
      ↓
Lock / Resource
      ↓
Cross-Layer Trace
      ↓
Incident / Performance Analysis

3. Relational Schema Notation

The following notation is used throughout this document:

PK = Primary Key
FK = Foreign Key
UK = Unique Key
NN = NOT NULL

Example:

USERS(
    user_id PK,
    username UK,
    uid_linux UK
)

means that:

user_id uniquely identifies a user.
username must be unique.
uid_linux must be unique.

32. Example Cross-Layer Scenario

Consider an online shopping application.

A user clicks:

BUY LAPTOP

The application runs as:

Linux PID = 4211

The OS monitoring layer records:

OS_EVENT
event_id = 501
pid = 4211
event_type = file_write
timestamp = T1

The DBMS layer records:

TRANSACTION
transaction_id = 100
pid = 4211
status = ACTIVE

The transaction performs:

UPDATE inventory

This is recorded as:

TRANSACTION_OPERATION
operation_id = 1001
transaction_id = 100
operation_type = UPDATE

The transaction obtains a lock:

LOCK
lock_id = 900
transaction_id = 100
lock_type = EXCLUSIVE
lock_status = GRANTED

The correlation engine creates:

EVENT_CORRELATION
correlation_id = 1
os_event_id = 501
transaction_id = 100
operation_id = 1001
correlation_type = PID_MATCH

The platform can then create:

CROSS_LAYER_TRACE
trace_id = 50
pid = 4211
transaction_id = 100

The final logical story becomes:

USER
 ↓

 ↓
LINUX PROCESS
PID 4211
 ↓
FILE / SYSTEM ACTIVITY
 ↓

 ↓

33. Deadlock Scenario

Suppose two transactions are running:

T1 → Lock A
T2 → Lock B

Then:

T1 requests Lock B
T2 requests Lock A

The system becomes:

T1 ───── waits for ─────> T2
 ↑                         |
 |                         ↓
 +────── waits for ───────+

This creates a cycle in the wait-for graph.

The DBMS analysis layer can identify:

Cycle
 ↓
Potential Deadlock
 ↓
Incident

The incident can then be associated with:

CROSS_LAYER_TRACE

allowing the dashboard to show both DBMS and OS context.

42. Normalization

The database should avoid unnecessary duplication.

For example, user information should not be copied into every process.

Instead:

USERS
  |
  ↓
PROCESSES

Similarly, transaction information should not be duplicated into every
operation.

Instead:

TRANSACTIONS
  |
  ↓
TRANSACTION_OPERATIONS

This supports relational database normalization.

47. Final Objective

The database is not simply a collection of OS tables and DBMS tables.

Its primary objective is to make it possible to connect the two layers.

The important relationship is:

OS BEHAVIOR
     +
DBMS BEHAVIOR
     ↓
CROSS-LAYER CORRELATION
     ↓
ROOT-CAUSE / PERFORMANCE VISIBILITY

This relational design provides the database foundation for the OS-DBX
platform.
